# 代码执行契约

## 目标

代码实施必须与当前项目真实生效的规范一致。通用语言最佳实践只在项目没有明确约定时补位，不能覆盖项目的格式、命名、目录、接口和实现范式。

## 实施前：建立规范上下文

修改代码前完成最小必要检查：

1. 读取当前文件所在目录生效的全局、仓库和子目录 `AGENTS.md`。
2. 检查项目现有工具与配置，例如 `.editorconfig`、ESLint、Prettier、Biome、Stylelint、tsconfig、语言 formatter、构建脚本和代码生成器。
3. 检查 `package.json`、Makefile、任务脚本或项目文档中已有的 lint、format、typecheck、generate 和 test 入口。
4. 在同目录、同模块或相同职责代码中选择一至三个稳定范例，确认项目实际采用的写法。
5. 将本次 `Conventions` 明确为：生效指令、工具配置、邻近范例和需要执行的检查。简单修改可以在内部完成，不要求机械输出给用户。

## 规范优先级

发生差异时按以下顺序判断：

1. 当前目录实际生效的 `AGENTS.md` 和用户已确认要求；
2. 项目已有 formatter、linter、编译器、生成器和 CI 配置；
3. 仓库正式开发文档和贡献规范；
4. 同模块、同职责的现有稳定代码；
5. 语言或框架通用惯例。

上层规则与自动化配置明显冲突，且会影响实现或验证时，不自行选择方向；保留证据并交回主 Agent 判断。

## 实施中：保持项目一致性

1. 新文件沿用邻近文件的目录、命名、导入顺序、导出方式、类型表达、错误处理、日志、注释和测试组织方式。
2. 修改现有文件时保持局部风格，优先最小正确改动，不顺手重构或格式化无关区域。
3. 不自行引入新的 formatter、linter、依赖、目录层级、基础类、工具函数或抽象；任务确实需要时必须有明确收益和范围依据。
4. 生成代码、锁文件、迁移文件和协议产物按项目既有生成流程修改，不手工模拟生成结果。
5. 使用项目已有 formatter 时限制在改动范围内；若工具必然产生大范围变化，先判断影响并避免混入当前增量。
6. 不把个人偏好或通用“最佳实践”强加给代码库，也不为了统一风格改动历史代码。

## 实施后：检查与报告

1. 检查增量 diff，排除无关格式化、换行变化、import 批量重排和超范围修改。
2. 按 [分级测试与验证规则](validation.md) 执行项目已有的 T1 检查；没有相应脚本则标记跳过，不强行新增配置。
3. 实现结果至少记录：修改内容、规范来源、关键邻近范例、实际检查结果和未解决冲突。
4. 发现风格或配置冲突时，相关 Agent 返回证据和影响，主 Agent 决定修复、接受现状或调整契约。
