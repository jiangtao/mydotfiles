# 增量 Review 规则

## 开始条件

1. 明确本次改动目标、范围、完成标准和固定基线，例如 commit、branch、tag 或 merge-base。
2. 读取当前增量对应的 T1 本地开发验证、T2 单测和 T3 端到端测试报告；需要补充时只运行当前环境可安全执行且与改动相关的检查。
3. 将失败、跳过、受阻和过期结果写入 Review 结论并说明影响；Review Agent 不因单项结果自行阻断整个流程，由相关 Agent 和主 Agent 决定修复、继续或交付。

## Review 范围

使用 `incremental_reviewer` 角色：`model="gpt-5.6-sol"`, `model_reasoning_effort="high"`, `sandbox_mode="read-only"`。

重点检查：

- 是否满足原目标、范围和验收标准；
- 正确性、状态一致性、安全性和回归风险；
- 接口、数据、兼容性和失败处理；
- 缺失或无效测试；
- 仅当会造成实际缺陷风险或显著阻碍后续修改时，检查冗余、可读性和维护成本；
- 是否遵守生效的项目代码规范、工具配置和同模块既有范式；
- 是否出现无关格式化、批量重排 import、换行变化或超范围重构；
- 与项目 `AGENTS.md`、规范和可信源是否冲突。

只报告对本次增量有实际影响的问题。纯风格建议只有在影响理解、正确性或维护成本时才提出。

## 事实、公正与克制

1. 每个问题必须有具体触发条件、实际影响和可复查证据；缺少其中任一项时，不作为确定缺陷报告。
2. 区分已确认问题、待验证风险、非阻断建议和已验证事实，不把推测写成事实，也不把建议提升为阻断问题。
3. 严重度只按可复现性、影响范围和后果判断，不因代码写法不符合个人偏好或通用最佳实践而夸大。
4. 不重复报告同一根因，不为显得全面而罗列低价值边角问题，不审查固定基线之外的历史代码。
5. 证据不足或存在合理解释时，明确写出不确定性和验证缺口，保持中立，不预设作者或实现有错。
6. 核对上下文、项目既有范式和相关测试；支持问题的证据与否定问题的反证具有同等权重。

默认不报告以下内容：

- 固定基线之前已经存在且未被本次改动放大的问题；
- 不影响行为、理解或维护成本的格式、命名和个人风格偏好；
- 当前实现正确时，仅仅“也可以这样写”的替代方案；
- 没有现实触发路径、影响或证据的假设性风险；
- 与当前目标无关的未来扩展、微优化或泛化建议；
- 已由更根本问题完整覆盖的重复症状。

## 修改边界

- 实施任务中的交付 Review：可以修复已授权范围内的问题，重跑受影响检查，再复审增量。
- 用户独立发起的 Review：保持只读，报告问题和验证缺口；没有修复授权时不修改代码。
- 规则、方案和文档 Review：按内容目标与证据审查，不机械运行代码 pipeline。

## 输出

1. 先列阻断问题，再列非阻断建议，最后列已验证事实。
2. 每个问题说明严重度、触发条件、影响、证据位置和建议修复方向。
3. 没有可执行问题时明确报告未发现问题，同时说明验证边界。
4. Review 结论不能替代未执行的测试或业务验收。
5. 只有会阻止目标达成、造成明确安全或数据风险、破坏兼容契约，或使必要测试确定失败的问题才能列为阻断问题。
