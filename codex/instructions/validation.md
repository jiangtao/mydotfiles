# 分级测试与验证规则

## 目标

测试用于形成可复查证据和风险反馈，不由测试 Agent 自动决定是否停止实施或交付。相关 Agent 接收报告并处理范围内问题，主 Agent 结合项目契约、任务目标和风险作最终决策。

每一级结果统一标记为：`通过`、`失败`、`跳过` 或 `受阻`。各级相互独立，不因高等级通过而推定低等级已经执行。

## T1：开发本地验证

1. 检查项目已有的 lint、ESLint、tsc、formatter、语法和类型验证入口，并确认使用项目现有配置。
2. 只运行与当前改动相关且项目已经具备的检查；项目没有对应工具或脚本时标记为 `跳过`，不强行安装、不新增配置。
3. 编译、lint、ESLint、tsc 和日志采集直接运行确定性命令，不创建子 Agent 只为执行脚本。
4. 检查增量 diff 是否出现无关格式化、换行风格变化或超出任务范围的自动修复。
5. 记录实际命令、作用范围、结果摘要和关键错误位置。

## T2：单元测试

1. 优先执行单元测试。项目已有测试框架、脚本和目录约定时，严格遵守现有约定。
2. 前端及其他项目没有相关单测时可以标记为 `跳过`，不为满足形式强行搭建测试体系。
3. 后端项目严格执行与改动相关的单测；重点覆盖主流程、主要失败风险，以及事务、迁移、并发和数据一致性等实际风险。
4. 需要补测试时只补具备回归价值的测试，避免复述实现的低价值用例。
5. 临时测试脚本不提交；只有具备长期回归价值且符合仓库规范时才转为正式测试。
6. 单个确定性单测命令由主 Agent 或实施角色直接运行；只有多步骤后端验证需要独立上下文、环境编排或专业判断时才使用 `backend_tester`。

## T3：端到端测试

1. 端到端测试默认非必须，由项目契约、任务目标或主 Agent 根据风险决定是否执行。
2. 用户可见行为、跨层集成、登录态、路由、持久化或真实浏览器交互发生变化，且 T1、T2 无法充分证明时，执行 T3。
3. 纯文档、内部类型调整、已有单测充分覆盖的纯逻辑修改和低风险重构通常跳过 T3，并在报告中说明依据。
4. 只验证真实主链路和关键可观察结果，不扩展为完整回归测试集。
5. 前端真实用户链路的浏览器验证默认使用当前设备已通过官方扩展连接、具有任务所需登录态和 Chrome Profile 上下文的真实 Chrome。确实需要 Agent 操作浏览器时使用 `e2e_tester`：`model="gpt-5.6-luna"`, `model_reasoning_effort="max"`。
6. 后端链路通过项目已有命令、API 或协议入口验证服务行为及数据副作用。多步骤验证确实需要独立上下文、环境编排或专业判断时使用 `backend_tester`：`model="gpt-5.6-luna"`, `model_reasoning_effort="max"`。
7. 前端与后端 Tester 保持独立职责；跨前后端链路由主 Agent 拆分验证目标、分别接收报告并统一判断，不让任一 Tester 兼任另一角色。
8. `e2e_tester` 执行前确认 Chrome 已连接、目标 Profile 正确、任务所需登录态有效，并且只操作明确允许的标签页、站点和账号范围。未满足时报告受阻，不自行安装额外 Skill、CLI、浏览器扩展或测试框架，也不重复创建无关环境。
9. 内置浏览器只可在用户或主 Agent 针对当前任务明确接受时作为隔离验证环境；报告必须标明环境差异，且不得用其结果证明真实 Chrome 登录态、Profile、标签页或扩展相关链路已经通过。
10. `backend_tester` 只使用任务包明确授权的本地或隔离测试环境和测试数据，禁止访问或修改生产环境、未授权共享环境或真实用户数据。
11. 两个 Tester 均固定使用 Luna Max；超出能力时返回已有证据、限制和受阻原因，由主 Agent 决定后续方案，不在角色内切换模型。
12. 前端报告记录浏览器环境、Chrome Profile 是否匹配、登录态前置条件、入口、操作步骤、预期行为、实际行为和失败证据；后端报告记录环境、前置条件、命令或请求、输入、数据副作用、清理结果和关键日志。报告不得记录账号凭证、Cookie、Token 或与验收无关的个人浏览数据。

## 测试报告

每次工程变更按适用级别输出一份简明报告：

| 字段 | 内容 |
|---|---|
| 级别 | T1、T2 或 T3 |
| 状态 | 通过、失败、跳过或受阻 |
| 范围 | 对应模块、文件、接口或用户主链路 |
| 执行 | 实际命令、测试入口或浏览器方式 |
| 证据 | 结果摘要、关键日志、截图或复现位置 |
| 影响 | 对当前目标、回归风险和交付判断的影响 |
| 建议 | 修复、继续、补测、接受风险或等待外部条件 |

## 反馈与决策

1. 测试报告交给实施或修复该范围的相关 Agent，同时交给主 Agent。
2. 相关 Agent 在已授权范围内处理实现问题并更新结果；需求歧义、范围变化、架构取舍和权限问题交回主 Agent。
3. 失败、跳过或受阻不会由测试 Agent 自动卡住整个执行流程，但不得隐瞒、改写为通过或声称对应风险已经消除。
4. 主 Agent 根据项目契约、任务目标、影响范围和风险决定继续实施、修复后复测、带风险交付或暂停。
5. 测试报告提供技术证据，不替代业务验收。
