# 可信源协作规则

## 目标

可信源用于保存项目当前有效的需求、决策、约束和验证结论，使后续任务不依赖完整 Session 才能恢复上下文。Session 仍保存探索过程，不能直接充当长期事实库。

## `$kn` 参考资料边界

`$kn` 当前是项目映射下的个人参考资料库，不属于默认可信源。其一级目录对应相关项目仓库，主要保存近期需求、方案、学习笔记、启动说明和架构分析。

`$kn` 可能存在重复正文、候选方案、未同步修改和过期结论。引用其中内容时必须：

1. 先确定对应项目仓库及其已经约定的知识契约；
2. 查找 `$kn` 条目的原始需求、决策或代码证据；
3. 与当前项目文档、代码、配置、测试和运行结果交叉核验；
4. 将无法核实的内容标为参考或候选，不得升级为当前事实。

当前不自动清洗、迁移或回写 `$kn`，也不把它声明为 LLM-wiki。后续完成去重、状态治理和 llm-wiki 接入后，再通过明确的项目契约调整其地位。

## 适用场景

以下任务需要读取本规则：

- 需求澄清、PRD、TRD、ADR 或架构方案；
- 涉及 `KNOWLEDGE.md`、Workspace Map、项目知识库或把 `$kn` 作为参考材料；
- 实现改变了已记录行为、接口、数据模型或运维方式；
- 测试或线上证据推翻了现有结论；
- 任务明确要求沉淀、同步或回写结论。

## 信息模型

1. **来源 Source**：原始需求、用户原话、Issue、代码、配置、日志、测试、真实运行结果和官方资料。
2. **决策 Decision**：已确认的需求方向、架构选择、取舍及适用范围。
3. **实施 Implementation**：当前代码、配置、迁移和发布状态。
4. **验证 Verification**：证明实际行为的测试、请求、页面、日志和业务样例。

每条稳定结论至少保留：结论、来源、适用范围或版本、状态、确认或验证日期、失效条件。项目已有字段时沿用，不强制迁移格式。

## 状态语义

- `candidate`：有来源但尚未确认，只能用于澄清。
- `confirmed`：需求或设计已经有权决策者确认，可以指导授权范围内的实施。
- `implemented`：实现已经落地，但不代表行为已验证。
- `verified`：适用验证已经通过，并记录了证据。
- `superseded`：已被新结论明确替代，历史来源仍保留。
- `invalid`：证据证明结论不成立，并记录原因。

“决策是否确认”和“实施是否验证”是两个维度。项目已有双字段时保留双字段；使用单状态时也不得把 `confirmed` 当成 `verified`。

## 读取流程

1. 读取当前目录生效的 `AGENTS.md`。
2. 按项目已有契约定位最小相关可信源；入口、优先级或映射不明时不得猜测。
3. 只有需要补充历史背景时才读取 `$kn` 对应项目目录，并将其标记为参考来源。
4. 只读取与当前 Goal 直接相关的最小页面和来源。
5. 将可信源中的“应有行为”与代码和运行证据中的“实际行为”分开核对。
6. 发现冲突时保留双方来源、版本和范围，判断实现偏差、文档过期或需求变化；涉及业务和架构取舍时进入需求澄清。

## 写入权限

只有满足以下任一条件时可以直接回写：

1. 项目的 `AGENTS.md`、知识契约或明确配置授权该类结论自动回写；
2. 用户当前任务明确要求更新、同步或沉淀可信源。

否则只能生成候选更新，说明目标位置、依据和待确认责任方，不能新建知识体系或报告为已回写。

即使允许自动回写，以下边界仍然成立：

- 已确认需求的实施状态和可复现验证结果，可以按项目契约更新；
- 未决业务规则、产品范围、架构取舍和会改变团队共识的内容，先标为 `candidate` 并交回主 Agent 澄清；
- 新证据不得静默覆盖历史结论，必须记录替代关系、适用版本和来源；
- 模型推断、记忆总结和无来源的 Session 摘要不得写成事实。

## 回写与验收

1. 将结论写入项目声明的权威页面，不在多个文档重复维护同一事实。
2. `$kn` 不作为默认回写目标；只有对应项目契约或当前任务明确要求更新时才能修改。
3. 链接原始需求、代码位置、测试结果或运行证据；无法链接时记录可复查定位信息。
4. 复核差异、状态、适用范围、日期和失效条件。
5. 任务结束时只报告以下一种结果：
   - `已更新`：列出文件和稳定结论；
   - `待更新`：列出候选内容、原因和下一责任方；
   - `无需更新`：说明本次未产生长期有效的新共识。
